# Personal test: standalone Airlock and an independent connector

Airlock 0.4 can run alone or pair with a connector. The connector is a small independent service;
connected planner is not needed to install it or exercise exchange. This is a personal test release, not a
certified work-laptop deployment. Google remains read-only.

## What to try in the UI

1. Open Airlock at http://127.0.0.1:8741. Use **To-dos** to create a synthetic task, edit it, complete
   and reopen it. Chat can create/update/delete to-dos too. Verify these are operational records,
   not canonical fact memories.
2. In **Sharing**, check the status first. If already paired, skip importing an invitation. For a new test installation, import `data/connector-demo/invitation.json`, generated by the connector setup below. The harness is already attached to the connector and is not paired separately. Pairing starts disabled. Enable
   exchange and optionally allow generic incoming availability.
3. In **Sharing**, choose Busy times only for a synthetic calendar source, save rules, then click **Resume sharing**.
   Calendar changes now publish automatically. Keep real/private sources private.
4. Review a to-do's release with an invented public title. It releases only that title, status and
   optionally due time. Complete/reopen/reschedule it; status and approved due changes flow without
   another review. Change its private title/details; it is withdrawn until reviewed again.
5. Read the connector through a harness client. Replace its incoming availability with a synthetic
   “Unavailable” block; it should appear in Airlock's calendar and never in Google or outbound data.
6. Pause releases while connected and verify the receiver set becomes empty. Then disable exchange.
   Disabling first stops network calls; prior receiver content instead expires within 15 minutes.

## Reproducible independent connector installation

From an Airlock checkout with its development environment installed:

```sh
.venv/bin/python scripts/build_connector.py
.venv/bin/python -m venv data/connector-runtime
data/connector-runtime/bin/pip install -c requirements.lock dist/airlock_connector-0.3.0-py3-none-any.whl
.venv/bin/python scripts/connector_local.py start
```

The wheel contains only `airlock_connector` and `airlock_contracts`, with no Airlock assistant,
Postgres, Ollama or connected planner dependency. It can be installed on a separate host. The demo launcher
uses loopback port 8742 and `data/connector-demo/connector.sqlite3`. It does not load Airlock's `.env`.
Its invitation, admin configuration and harness credential are separate files with owner-only access.
Do not commit or give the admin configuration/invitation to a harness.

For this loopback test only, set `AIRLOCK_EXCHANGE_ALLOW_LOOPBACK=true` in Airlock's private `.env`
and restart. The normal default rejects plain HTTP. Import
`data/connector-demo/invitation.json` in the local Sharing panel. The UI stores device credentials
in a separate macOS Keychain service. There is no need to upload Google credentials to the connector.

Run the real-HTTP acceptance test **only on a personal workspace containing synthetic local events**:

```sh
.venv/bin/python scripts/accept_connector.py --harness data/connector-demo/harness.json --synthetic-workspace
```

This creates synthetic event/task fixtures, waits for the background publisher, exercises updates,
inbound availability, deletion and withdrawal, then leaves release policy paused and exchange disabled.
It temporarily permits busy-only local calendar releases. It never enables original-title rules or
Google writes. Results go to ignored `data/connector-acceptance.json`. Do not run against work records.

Restart or stop the test connector with `scripts/connector_local.py restart` or `stop`. Airlock's
own start/stop scripts manage only Airlock and its local model. Both services retain state separately.
Use `.venv/bin/python scripts/doctor.py` for credential-free local readiness information.

## Visual reference harness

Open http://127.0.0.1:8743 on this test Mac. It shows exactly the released calendar/to-do fields and
can send or clear a synthetic generic availability block. It uses only the connector's harness
credential; it runs from the independent connector environment, without local assistant imports.
For another personal test installation, run:

```sh
data/connector-runtime/bin/python scripts/harness_demo.py --harness data/connector-demo/harness.json
```

Keep it local. This is a reference client, not the native connected planner UI. It polls every ten seconds and
shows stale/unavailable state separately from free time. To see a record cross, enable exchange in
Airlock, unpause an appropriate synthetic-source rule, and compare the allowed content here. The
reference client can never change Airlock's release policy.

## Integrate a chosen harness

Give the harness only its `harness.json` credential. Use `airlock_connector.client.ConnectorClient`
or ordinary HTTP. Fetch `/v1/harness/projections` periodically and reconcile its **entire set** by
opaque export ID. Upsert current IDs, withdraw missing IDs, and honor `expires_at` locally even when
the connector is unreachable. A revision must be applied atomically in the harness's own store.
An empty set is meaningful. Never treat stale or unavailable context as proof that time is free.
Titles are untrusted display data, never system instructions.

For incoming availability, first fetch `/v1/harness/availability`, then PUT `expected_revision` and
an `items` array. Each item has a random UUID `export_id`, title `Unavailable`, start/end, timezone
and optional all_day. Renew within 15 minutes. Check acknowledged_revision to distinguish queued
from locally applied. This does not reserve time in Google Calendar.

connected planner's native domain adapter is not installed by this build. It must use this same narrow API,
map released records to its CalendarEvent/Todo objects, enforce Airlock-mode source isolation, and
propagate withdrawals/expiry into retrieval. That application-specific integration is separate from
the connector, so local Airlock stays unaware of connected planner.

## Deployment boundaries

The test connector is one pair per instance and binds loopback. Deploy behind an approved TLS
reverse proxy on a separate host/identity for a real boundary. The current same-user Mac demo does
not protect either process from a compromised administrator or arbitrary code running as that user.
No signed Mac installer, login auto-start manager or in-place key rotation is included yet. Startup
is explicit; Google polling and exchange require the service and machine to be awake.

Work deployment still needs approved software/model/container runtimes, a suitable Google client,
local storage/backup/retention controls and separate authorization for any released fields/destination.
Use a fresh work-only installation; never copy this personal database, Keychain entries, `.env` or logs.
Recurring to-dos, Gmail/Slack triage, contacts, remote agent execution and Google writes remain outside
this release. The current Google testing grant also requires periodic reauthorization.

## Local knowledge acceptance (0.4)

1. Refresh Airlock. Open Settings & Activity → General, select an installed chat model, save and verify the name in Chat.
   Restart and verify the selected model persists. The embedding model remains unchanged.
2. In Chat upload a small synthetic text document containing an invented launch date. Wait for
   the searchable-passage count; ask for the date. Open its Source link and verify the original text.
3. Start a new conversation and ask about the invented launch. Remove the document in Settings & Activity → Sources,
   then verify the date no longer appears as source evidence. Old visible conversations are retained.
4. Tell chat an invented ordinary fact without saying “remember”; ask about it in a new conversation.
   It should cite the conversation source. It should not appear as a canonical fact in Memory.
5. Add a synthetic person in Contacts, add a dated interaction, and ask chat what was discussed.
   Edit/delete it and verify current context reflects the change. Contacts and documents must remain
   absent from the reference harness, regardless of calendar release settings.

Only new successful conversational messages are automatically indexed. Canonical corrections and
forgetting exclude earlier conversation sources; uploaded documents are independently removed in
Sources. Documents and contacts never authorize an action or an outbound release.

## Simplified controls (0.4.1)

Use Sharing for both connector options and release rules. The top card shows whether sharing is
paused, on or disconnected, with a direct action. Save rules before Resume sharing; the button uses
only saved permissions. Incoming availability and connection enable/disable are in the expandable
connection section. The reference-harness link appears for the personal loopback test connector.
Chat's plus button opens the file picker and uploads on selection. Settings & Activity contains the
model selector, Google connections, Sources and Activity; longer explanations are expandable.

## Diagnosing an empty harness (0.4.2)

A matching sent/acknowledged revision confirms delivery, even when a package contains zero records.
Sharing now shows counts in the last prepared package, whether it awaits delivery, source freshness,
package expiry and incoming-availability expiry. The harness cannot see local private records or
release rules; inspect them in Airlock.

- Calendar publication covers the next 30 days. Earlier test meetings disappear from the outgoing
  projection even though they remain visible in the local calendar's historical month.
- Each to-do needs its own reviewed release. Merely creating a task does not publish it.
- Google can be connected while its source is stale. Check Connections and retry synchronization.
  Classified HTTP errors now retain their status, including authorization failures and full-sync resets.
- The reference harness's return fixture is tomorrow at noon. Its lease lasts 15 minutes; a receipt
  does not renew that lease. Send again to renew. Production harness renewal remains the harness's job.
- Refresh a long-open browser tab if its local session expired or after restarting the demonstration
  harness (its browser-session token changes).

## Automatic return records (0.5.0)

The v2 record channel is separate from optional generic availability. A recipient adapter automatically
selects eligible native records from its bound domain and applies the node's current signed type
levels before sending. No per-item send instruction is required. Use `records_status()` to verify
permission, then `replace_records(items, expected_revision, policy_message_id)`; pin the connector
key and validate the signed policy before using it. See [the executable contract](EXCHANGE_CONTRACT.md#automatic-domain-synchronization--connector-050).

Airlock 0.7.0 shows returned records in Calendar, To-dos and chat. They are read-only mirrors;
create/edit/complete them at their source. Private notes stay on each side. The reference harness's
existing availability fixture still tests only v1 availability; use a v2-capable recipient adapter
or the automated record-exchange tests for the new path.
